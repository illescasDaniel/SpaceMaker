codenav/webnav: intent-level tools, workspace-wide CSS index, multi-line diagnostics.

- **Context:** Live testing surfaced three gaps: (1) ty's multi-line diagnostic messages (e.g. `Code is unreachable` with a second unprefixed continuation line) broke the "one issue per line" output contract. (2) The API mirrored the LSP 1:1, forcing agents through `search_symbol` → column arithmetic → separate `hover`/`definition`/`references` calls just to answer "what is this" or "who calls this"; and `implementation`/`typeHierarchy.subtypes` return nothing for this codebase's hexagonal ports, since ports are `Protocol`s and adapters never explicitly subclass them — "which adapters implement this port?" (the most common question in a hexagonal codebase) was unanswerable. (3) The CSS/HTML language servers only see one file at a time, so `var(--custom-property)` and `#id`/`.class` selector usages couldn't be cross-referenced across files, even though `--x` is defined once in `theme.css` and used everywhere.
- **Decision:** (1) `format_diagnostic` splits multi-line messages, indenting continuation lines 4 spaces, and includes the diagnostic `code` when present. (2) New name-based composite codenav tools — `symbol_info`, `outline`, `callers`, `implementations` — backed by a shared `resolve_symbol()` (`_shared/resolve.py`, dotted `Class.method` support, ambiguity via candidate list rather than guessing) and new `LspClient` methods (`document_symbol`, `prepare_call_hierarchy`, `incoming_calls`, plus scratch-document methods for in-memory probes). `implementations` verifies structural `Protocol` conformance with a two-stage approach: method-name-set candidate matching, then an in-memory probe document (`didOpen` at `<root>/.codenav_probe.py`, never written to disk) with `def _p(x: Candidate) -> Port: return x`, checked via ty's real `invalid-return-type` diagnostic — not just a name-match heuristic. (3) New pure-Python `webnav_mcp/web_index.py` scanner (regex/brace-stack grade, no language server, rescans every call — ~20 files, a few ms) indexes `--custom-property` declarations/usages and `#id`/`.class` selector hits across `.css`/`.html`/`.js`, grouped into two separate roots (`static`, `wireframes`) since they define their own values/markup. New `css_var`/`selector` tools; `references`/`definition` answer from the index automatically when the cursor is on one of those tokens in a `.css`/`.html` file; `diagnostics` gets undefined-var and unreferenced-selector warnings appended for those file types. A JS selector built from string concatenation (one real case, `app.js`) is recorded against only its static prefix and tagged "dynamic partial match" rather than dropped or guessed.
- **Rationale:** Composite, name-based tools match how agents actually ask questions about code, cutting a 3–4 call chain to one. ty's structural-typing gap for `Protocol` ports needed a real type-checker verification step, not a name-match guess, to stay trustworthy. The CSS/selector index fixes a concrete, previously-documented single-file limitation without pulling in a real CSS parser or `@import` resolution — accepted as out of scope, since none of that machinery is needed for this codebase's actual patterns. MCP prompts/resources were considered and rejected: prompts are user-invoked slash commands an agent never calls, and resources require an explicit fetch step; server `instructions` and tool docstrings (already in context) are the actual lever for agent behavior. Also found live: firing ~86 concurrent `documentSymbol` requests (`asyncio.gather`) made ty respond with `"content modified"` errors — fixed by awaiting them sequentially instead (still sub-second for this codebase).
