Gallery at 50k+ items: derived SQLite index (amends "no database"), cursor pagination, frontend DOM windowing; per-connection query lock added after finding a real concurrency bug.

- **Context:** User asked to analyze and fix gallery performance for a 50,000-image library. Investigation found two compounding bottlenecks: `AppServices.captured_at_map` re-walked `converted/` and re-probed EXIF for **every** file whenever *any single file* changed (a delete or convert-completion called `invalidate_gallery_metadata_cache()`, wiping the whole cache, not just the changed entry); and `/api/gallery/timeline` returned the entire library in one JSON response, rendered as one synchronous DOM-append pass in `app.js` (50k `<button><img>` nodes in one tick). `docs/ARCHITECTURE.md` stated "no database" as an explicit principle, so amending it needed to be a deliberate, surfaced decision rather than an incidental side effect.
- **Decision:** Full SDD cycle, every gate approved in chat before proceeding. (1) A derived, fully-rebuildable SQLite index (`{library_root}/.index.sqlite`, `SqliteGalleryIndex` behind a new `GalleryIndexPort`) replaces the in-memory cache — the filesystem stays the source of truth; the index is safe to delete at any time and rebuilds itself. (2) A new `SyncGalleryIndex` use case diffs `converted/` against the index by `(mtime, size)` and only re-probes EXIF for files that are new or actually changed, not the whole library. (3) `GalleryCursor` is a compound `(captured_at, relative_path)` keyset, not `captured_at` alone, because ties are common in practice (every EXIF-probe failure falls back to the same `datetime.fromtimestamp(0)`). (4) `to_epoch_seconds`/`from_epoch_seconds` (`domain/gallery_index.py`) use a fixed UTC offset instead of `datetime.timestamp()`/`fromtimestamp()`, because those go through the OS's local `mktime` and raise `OSError` on Windows for dates at/before 1970 — hit this directly via the existing `year=1970` calendar integration test. (5) `/api/gallery/timeline` is now cursor-paginated (`?cursor=&limit=`); a new `/api/gallery/item/neighbor` endpoint replaces the old full-client-side-path-array approach for Prev/Next. (6) `app.js`'s `loadGallery()` does infinite scroll (`IntersectionObserver` + sentinel) with DOM windowing at month-block granularity — mounted tiles capped around 1200, blocks scrolled far above the viewport become height-pinned `.month-placeholder` divs, remounted on scroll-back.
- **Bug found and fixed during manual verification (not by unit tests):** `SqliteGalleryIndex` originally locked only around connection *creation* (`_connect()`'s dict lookup), not around query *execution*. Manually testing Prev/Next in a real browser (which fires two parallel `/api/gallery/item/neighbor` requests) reproduced `sqlite3.InterfaceError: bad parameter or other API misuse` on the very first click, every time — concurrent `execute()` calls on the same `sqlite3.Connection` from different request-handling threads aren't safe even with `check_same_thread=False`. Fixed by making `self._lock` a `threading.RLock` (reentrant, since `_connect()` also acquires it) and wrapping every public method's full body in `with self._lock:`. Added a multi-thread regression test (`tests/unit/test_sqlite_gallery_index.py`) that fires many concurrent reads at one instance and asserts no exceptions.
- **Rationale:** The two things actually worth caching were re-probing (subprocess-per-file, genuinely expensive) and re-walking-on-every-request (cheap per call but still O(n) and done on every page load) — a derived SQLite index fixes both while keeping "filesystem is the source of truth" intact, which is why amending "no database" to "no database of record" was judged acceptable rather than a violation of the original principle's intent. The concurrency bug is called out specifically because it was **not** caught by any unit test (the fakes and the single-threaded adapter tests all passed) — it only surfaced under real concurrent HTTP requests in a real browser, reinforcing that this kind of adapter needs at least one real concurrency test, not just correctness tests against a single caller. Verified: `uv run pytest tests/unit tests/integration` (excluding the pre-existing unrelated `test_qt_webengine_shutdown.py` qtpy-import failure) — 208 passed; ruff/ty clean (ty's remaining diagnostics are the same pre-existing qtpy/PyQt6 ones as before this work). Biome (`npm run check`) was **not** run — no `npm`/`node` available in this sandbox; flagged to the user as a pending check.
