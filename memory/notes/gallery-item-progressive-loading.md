Gallery item detail: real-thumbnail-first progressive loading, photo-app open animation, slide transitions on prev/next; fixed a `.gallery-item-stage` centering regression.

- **Context:** User asked for the gallery photo-detail flow to feel like an app, not a website: opening a photo should animate like an entrance rather than a hard cut; prev/next navigation should slide; and while the full image/video is still loading, the preview area should show the item's real thumbnail plus a spinner instead of collapsing to near-zero height and jumping once the full media arrives. Confirmed with the user that every saved photo already gets a generated thumbnail in production (`SubprocessThumbnailGenerator`, served at `GET /thumbs/{relative_path}`), so the placeholder is the real thumbnail, not a synthetic blur. Full SDD cycle run: Phase 0 wireframe (`wireframes/app.html`) approved ("i like this, that's the idea... design is fine, let's advance"), Phase 1 spec (`specs/ui-motion/SPEC.md`, `specs/gallery/SPEC.md`) approved ("proceed"), Phase 2 architecture approved ("okay") before Phase 4 touched production code.
- **Decision:** `app.js`'s `setStageLoading()` now builds a `.gallery-item-media` wrapper containing `.gallery-item-thumb` (the real `/thumbs/{path}` image) and `.gallery-item-spinner` immediately, before the full-resolution media has even been requested; `renderGalleryItemStage()` injects the real `<img>`/`<video>` into that same wrapper and reveals it (`.loaded` class, hiding thumb+spinner) only on the media's `load`/`loadeddata` event, so the box never collapses. `shiftGalleryItem()` (prev/next) slides the current media out (`slide-out-next`/`slide-out-prev`, 160ms) before swapping content and sliding the new one in (`slide-in-next-start`/`slide-in-prev-start`, cleared via `void media.offsetWidth` to force a reflow so the browser doesn't coalesce both transform states into one paint) — this only runs for prev/next; a fresh open (thumbnail click, direct route) still uses the container-level `#view-gallery-item.screen.active` zoom+fade (`gallery-item-in` keyframe) instead. Applied identically across the desktop shell (`index.html`), mobile shell (`shell-gallery.css`), and the wireframe reference.
- **Bug found and fixed during manual verification:** the user reported the gallery item preview was no longer horizontally centered. Root cause: `.gallery-item-stage` had `aspect-ratio: 4/3` and `max-height` but no explicit `width` — when a full-width stretch would produce a height exceeding `max-height`, browsers clamp the height and then *re-derive* a narrower width from that clamped height to preserve the ratio, shrinking the box itself; with no `margin: auto`, it then sat left-anchored instead of centered. An intermediate fix attempt (`margin: 0 auto` alone) made it worse — the grid item's default `justify-self: stretch` was disabled, and since its children are all `position: absolute` (contributing ~0 intrinsic size), the box collapsed to ~58×44px. Fixed by adding `width: 100%;` to `.gallery-item-stage` instead, in all three files (`index.html`, `shell-gallery.css`, `wireframes/app.html`) — this keeps width a definite, independent value so `aspect-ratio`'s derived height can be clamped by `max-height` without recomputing width.
- **Rationale:** Real-thumbnail-first (rather than a synthetic blur-up placeholder) was chosen because the thumbnail already exists on disk for every photo — no new generation work, and it's visually accurate rather than a guess. Slide-out-then-swap (rather than a cross-fade or simultaneous slide) avoids the new item's slide-in fighting the container's own open animation on first render, since prev/next never re-triggers that container animation. Verified end-to-end in a live browser session against real gallery data (a 4:3 video and a portrait 1179×2556 image): zero console errors, `getBoundingClientRect()` confirmed the stage back at full container width post-fix, clean Biome lint (`npm run check`).
