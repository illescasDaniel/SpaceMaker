# Technical decisions

Append-only log (newest first). Never rewrite history.

## 2026-09-28 — `uv run task checks` runs natively (no bash required)

- **Context:** On Windows, `checks.py` invoked `shutil.which("bash")`, which often resolves to the WindowsApps WSL stub (`…\WindowsApps\bash.exe`). With no WSL distro installed that stub exits immediately (“no installed distributions”), so `uv run task checks` never ran the gate even when Git Bash was installed under `Program Files\Git`.
- **Decision:** Implement the quality gate steps (ruff, ty, pytest, npm check/format) directly in `scripts/quality/checks.py` via `uv`/`npm` subprocesses. Keep `checks.sh` as a bash-friendly mirror for CI/shell users; `web.sh --fix` now calls `npm run format` (there is no `fix` script).
- **Rationale:** The gate only needs Python tooling + optional Node — not a POSIX shell. Avoids PATH ordering traps between WSL stubs and Git Bash.

## 2026-09-28 — Code modernization: split hubs, aiosqlite, no HTTP/3

- **Context:** Production hubs exceeded 600 lines (`app.js`, `index.html` CSS, `services.py`, `app.py`). User asked for file separation, async HTTP honesty, strict typing, TypeScript, and HTTP/3 QUIC — then dropped HTTP/3 because TLS/certs are a poor fit for loopback desktop + LAN QR phones.
- **Decision:** (1) FastAPI `APIRouter` modules under `adapters/inbound/web/routes/`; `AppServices` mixins package under `bootstrap/services/`; shell CSS extracted to `static/shell-*.css`; shell UI authored in `web/src/*.ts` and emitted to `static/js/` (`main.js` ES module entry). (2) Gallery index uses **aiosqlite** with async `GalleryIndexPort` / use cases / gallery routes; sync workers bridge via `AppServices.run_coro` (helper-thread `asyncio.run` when already on the ASGI loop). Per-operation DB connections avoid cross-loop cache bugs. (3) **No HTTP/3 / TLS** — stay on uvicorn plain HTTP. (4) Strict TypeScript (`web/tsconfig.json`: `strict`, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`; core modules fully typed, feature modules migrate behind `@ts-nocheck`). (5) Production Python: ruff ANN on `src/spacemaker/`, ty-clean mixins via `self: AppServices`, TypedDict gallery serializers.
- **Rationale:** Keeps hexagonal boundaries while making files reviewable; async SQLite matches FastAPI without rewriting subprocess adapters; HTTP/3 would force cert UX on phones and pywebview for little localhost gain.

## 2026-09-28 — Thumbnails: drop long-lived HTTP caching instead of URL-versioning it; add an on-disk format-version marker

- **Context:** Follow-up to the "fit-within instead of crop-fill" entry below. That fix was correct at the generator level, but the user reported still seeing square thumbnails for `20945`/`20941`/`IMG_5237`/`IMG_5234` after it shipped. Root cause was two caches downstream of the generator, not the generator itself: (1) `/thumbs/{path}` was served with `Cache-Control: public, max-age=86400` and the desktop webview's HTTP cache is a persistent, on-disk profile (`~/.cache/spacemaker/webengine/<UI_SHELL_VERSION slug>/`) that survives app restarts — confirmed by inspecting the user's real profile cache, which held 49 stale 320×320 JPEGs including `/thumbs/20941.avif` and `/thumbs/20945.avif`; (2) the server's own `.thumbnails/` disk cache in `SubprocessThumbnailGenerator.ensure_thumb` only checked `dest.mtime >= source.mtime`, with no way to know the *method* used to build an existing cached file had changed, so a pre-fix square thumbnail already on disk would never regenerate on its own — correcting the previous entry's "self-heal on next request" claim, which was wrong.
- **Decision:** Asked the user whether to version the `/thumbs/` URL (keep long-lived caching, force a new URL per version) or drop long-lived caching outright. User's reasoning: thumbnail-format versions will be rare, and the loopback request for an already-generated ~10–50 KB thumbnail is effectively free — the expensive step (on-disk generation) is already cached separately — so the HTTP cache wasn't buying much. Decided: drop `max-age=86400` on `/thumbs/` in favor of `Cache-Control: no-cache` plus `ETag`/`If-None-Match` 304 revalidation (Starlette 1.6's `FileResponse` computes and sends an `ETag` from mtime+size but does not itself answer `304` on a matching `If-None-Match` — added that check in the route). Also added a small on-disk format-version marker (`THUMBNAIL_FORMAT_VERSION` in `subprocess_thumbnails.py`, one file at `thumbnail_format_version_marker_path()`) so a generator change invalidates old cached thumbnails going forward, closing gap (2) as well. `/media/` (full-size, several MB per file) deliberately kept on long-lived caching — real bandwidth/CPU savings there, and a relative path is only reused via **Reset gallery** or a same-name re-import, not a routine event; revisit only if it shows the same staleness bug. As the manual escape hatch for whatever this class of bug misses, also shipped Settings → **Clear browser cache** (no confirm — deletes only the webview's on-disk HTTP-cache/cookies/local-storage directory via a new `ClearBrowserCache` use case, self-regenerating, no library or preference data touched).
- **Rationale:** The `/thumbs/` route sits behind the app's own loopback server — same machine, same disk — so the marginal cost `no-cache` reintroduces (one small request + a stat-based ETag comparison) is negligible next to the correctness cost of a webview silently pinning stale bytes for up to a day after any generator fix, reset, or re-import that reuses a filename. Versioning the URL was the rejected alternative: it would have kept the caching win but adds a query-string/version-plumbing concern for a caching layer that turned out not to be worth much in the first place, and would not by itself have fixed gap (2) (still needed the on-disk marker regardless). Full SDD (wireframe → spec → architecture → tests → impl) approved in chat 2026-09-28.

## 2026-09-28 — Quality gate stale-failures fix: `gallery_cache_paths` outputs are OS-native filesystem paths, not URL fragments; CRLF was a local checkout artifact, not repo content

- **Context:** Investigated the 3 tracked `uv run task checks`/`npm run check` failure categories (`memory/progress.md` "Quality gate has stale pre-existing failures"). (1) `ruff format` wanted to reformat `sqlite_index.py`/`test_easy_convert_drain.py`/`test_progressive_avif_encode.py` — plain over-length-line wrapping, no behavior change. (2) `test_gallery_cache_paths.py`/`test_transfer_usb_files.py` asserted `str.endswith("/…")` with a hardcoded forward slash against `thumbnail_path`/`export_cache_path`/USB-transfer destination paths. Traced every caller of `thumbnail_path`/`export_cache_path`/`export_cache_paths_for_relative` (`export_friendly_media.py`, `gallery_cache_cleanup.py`, `subprocess_thumbnails.py`) — all wrap the result in `Path(...)` and use it purely as a filesystem path (open/write/delete), never in a URL; the `/thumbs/{relative_path:path}` route's URL-facing string is the *route parameter* from the incoming request, unrelated to this function's return value. So on Windows the native `\` separator in the output is correct, and the tests' POSIX-only assumption was the bug, not the domain code. (3) `wireframes/app.html`/`src/…/static/app.js`/`biome.json` showed CRLF to Biome locally, but `git show HEAD:<file>` proved the committed blobs are LF — this machine's `core.autocrlf=true` was converting LF→CRLF on checkout, and no `.gitattributes` rule overrode it (only `/.githooks/* text eol=lf` existed).
- **Decision:** (a) Applied `ruff format` as-is to the 3 files. (b) Fixed the 2 test files instead of the domain code: `test_gallery_cache_paths.py` now compares `Path(result) == Path(library) / ...` (matching the style of the adjacent `test_given_windows_separators_when_thumbnail_path_then_normalized`, which already tests input-side `\`→`/` normalization and was passing); `test_transfer_usb_files.py`'s union test now checks `Path(path).parts[-2:] == ("Download", "a.pdf")` / `Path(path).name == "notes.txt"` instead of `str.endswith(".../a.pdf")`. (c) Added `* text=auto eol=lf` to `.gitattributes` (ahead of the existing `.githooks/*` line) so every clone/checkout normalizes text files to LF regardless of local `core.autocrlf`; re-synced the working tree to match (`git add --renormalize .` + delete-and-recheckout the 3 previously-CRLF files, since a plain `git checkout -- <path>` was a no-op when git didn't think the blob had changed). Also fixed one real Biome lint finding in `wireframes/app.html:2782` (`useOptionalChain`: `if (outgoing && outgoing.parentNode)` → `if (outgoing?.parentNode)`) — wireframe edits don't require a Phase Gate per `AGENTS.md`. `uv run task checks` and `npm run check` both fully green afterward (447 passed, 8 skipped, same as before; 0 Biome errors/warnings).
- **Rationale:** Prefer the fix that matches how a value is actually consumed: `gallery_cache_paths.py`'s outputs are filesystem paths end-to-end, so native separators are correct and portable POSIX-only test assertions were the defect. `.gitattributes eol=lf` is the standard fix for CRLF-vs-LF drift caused by per-machine `core.autocrlf` — it's a one-time repo-level fix that prevents this class of failure from recurring on any Windows clone, rather than something to work around per-session.

## 2026-09-28 — `/new-worktree` skill: create worktree+branch then copy/regenerate `.venv`+`node_modules`

- **Context:** srxy has `.cursor/skills/copy-venv-to-worktree-srxy/`, which copies an already-existing worktree's `.venv` from the primary checkout (robocopy/rsync) and rewrites the absolute paths baked into shebangs/editable `.pth`/`direct_url.json` (`uv sync` alone doesn't fix these post-copy, https://github.com/astral-sh/uv/issues/18196), so no packages re-download. srxy has no "create worktree" skill because Cursor's background-agent feature creates those. SpaceMaker is driven from two tools with different worktree mechanics — Claude Code's native `EnterWorktree` tool creates `.claude/worktrees/<name>` (confirmed by the existing `gallery-thumb-fix` worktree), Cursor has no such tool and stays on manual `git worktree add` under `~/.cursor/worktrees/` — and is dual-stack: the quality gate also needs `node_modules` (`scripts/quality/web.sh` hard-fails without `node_modules/@biomejs/biome`), and has a `uv` workspace (`spacemaker` + 3 `mcp-servers/*` members) with several editable `.pth` files to rewrite, not one.
- **Decision:** New skill `.cursor/skills/new-worktree/` (mirrored to `.claude/skills/` via the existing symlink) does both steps. It always forks the new branch from the **currently checked-out branch** (plain `git worktree add -b <branch> <path>` with no start-point, so git defaults to `HEAD`) rather than delegating to `EnterWorktree`'s own `name`-based creation, whose default `baseRef: fresh` branches from `origin/<default-branch>` instead — a mutable per-session setting the skill must not depend on. In Claude Code it then calls `EnterWorktree({ path: ... })` ("enter an existing worktree" mode) purely for the session cwd-switch + `ExitWorktree` lifecycle bookkeeping. `scripts/copy-venv.sh` mirrors `.venv` (robocopy/rsync) + `rewrite_venv_paths.py` (adapted near-verbatim from srxy — already fully generic, no package name hardcoded) + offline `uv sync --group dev`, and mirrors `node_modules` the same way but with no rewrite step (registry-only devDependencies, no absolute paths in the npm `.bin/*.cmd` shims); both fall back to regenerating (`uv sync --group dev` / `npm ci`) when the primary checkout has nothing to copy. Also fixed `apply-worktree`/`delete-worktree`, which only recognized `~/.cursor/worktrees/` (copied verbatim from srxy's Cursor-only skills) — `delete-worktree`'s abort check would have rejected any `.claude/worktrees/` target — to recognize both worktree conventions and to prefer `ExitWorktree`/ `EnterWorktree({action:"keep"})` over Cursor's `move_agent_to_root` when the session got there via `EnterWorktree`.
- **Rationale:** A worktree the user is about to keep working on should branch from what they're currently on, not silently rebase the starting point to `main`; `EnterWorktree`'s `fresh` default would do exactly that unless overridden globally, which is a worse failure mode than the skill just setting up its own `git worktree add`. Copying rather than re-installing `.venv`/`node_modules` avoids re-downloading multi-package `uv`/npm dependency trees per worktree; falling back to regeneration keeps the skill usable even from a primary checkout that was never synced.

## 2026-09-28 — Thumbnail generation: fit-within instead of crop-fill, so the cached JPEG preserves source aspect ratio

- **Context:** `SubprocessThumbnailGenerator._thumb_image` used Magick `-thumbnail 320x320^ -gravity center -extent 320x320`, which scales to *cover* a 320×320 box and then crops the overflow — every cached thumbnail file is a hard square regardless of the source's real aspect ratio. `_thumb_video` extracted a full-resolution ffmpeg frame with no scaling at all. This mismatched the item-detail page, which already shows the thumbnail as a progressive placeholder via `object-fit: contain` (same aspect-fit as the full preview) — a pre-cropped square thumb doesn't line up with the full image's real framing, so the placeholder visibly "pops" into a different shape when the full image loads.
- **Decision:** User explicitly required (in chat) that thumbnail files preserve the source's exact aspect ratio, with cropping to a square remaining a **display-only** concern (grid `object-fit: cover`, unchanged). Changed `_thumb_image` to `-thumbnail 320x320>` (fit within a 320×320 box, longest side capped, proportional on the other axis; `>` skips upscaling smaller sources) with no `-gravity`/`-extent`. Changed `_thumb_video` to add `-vf "scale='min(320,iw)':'min(320,ih)':force_original_aspect_ratio=decrease"` so video thumbnails are also capped and aspect-correct instead of full-resolution. `specs/gallery/SPEC.md` gained an explicit "Thumbnail framing" bullet documenting this. New unit tests assert the exact Magick geometry string and the absence of `-extent`/`-gravity`, and assert the ffmpeg `-vf` scale filter.
- **Rationale:** Baking the square crop into the cached bytes was strictly worse than doing it in CSS: it threw away information the item-detail placeholder needed, for a benefit (matching the grid's square tiles) that `object-fit: cover` already gives for free at zero cost to the underlying asset. Verified against the real library (`C:\Users\kaumi\Pictures\SpaceMakerLibrary`, worktree-scoped dev server): source `IMG_5205.avif` is 3024×4032 (3:4); the old cached thumb was a cropped 320×320 square; after deleting it and re-requesting `/thumbs/IMG_5205.avif`, the regenerated file is 240×320 — exactly 3:4. Bulk-regenerating the rest of the real library's stale thumbnails was blocked by the auto-mode classifier (wildcard delete flagged as "Irreversible Local Destruction") even though `.thumbnails/` is documented as safe to delete anytime — left for the user to do (delete `.thumbnails/` or approve a permission rule), since old square thumbnails will simply be replaced by aspect-correct ones the next time each is requested (mtime-based staleness check won't force it on its own).

## 2026-09-28 — End-to-end verification caught a stray dev-server process bound to the wrong checkout's venv

- **Context:** While end-to-end verifying the convert-media fix (below) against the user's real library, `preview_start spacemaker-server` (which runs `uv run spacemaker --server-only --port 8765` per `.claude/launch.json`) launched a process whose command line (`Get-CimInstance Win32_Process`) showed `C:\Users\kaumi\Documents\Projects\SpaceMaker\.venv\Scripts\spacemaker.exe` — the **root repo's** venv, not this worktree's own `.claude\worktrees\gallery-thumb-fix\.venv`. `spacemaker.pth` in the root venv points at the root repo's `src/`; the worktree's own venv correctly points at its own `src/`. Running Convert against that server reproduced the *original* DNG failure (moved back to `error/`), because it was silently running the unfixed code from the shared checkout — not this worktree's staging-directory/`--ignore-xmp` fix. No log file appeared either, for the same reason (that checkout's `desktop.py` may lack today's `configure_logging()` call, or simply never got the chance to run it under whatever state that process was in).
- **Decision:** For any real dev-server verification in a worktree, don't trust `preview_start`'s server to be scoped correctly — after starting it, confirm with `Get-CimInstance Win32_Process -Filter "Name='python.exe'" | Where CommandLine -like "*<port>*"` that the command line's `.venv`/`spacemaker.exe` path is under the worktree directory, not the root repo. If it isn't, stop it and start the server directly (`uv run spacemaker --server-only --port <N>` from the worktree's own cwd via the Bash tool, backgrounded) instead of relying on `preview_start`. This is what actually converted `IMG_5234.dng` and regenerated the 3 missing thumbnails correctly on the second attempt (port 8766, worktree-scoped).
- **Rationale:** Avoids a false-negative ("the fix doesn't work") or false-positive ("the fix works") verification result caused by testing against the wrong code. Not something to "fix" in the repo — it's specific to how this local machine's dev-server tooling resolves `uv run` outside the worktree's own directory context; worth remembering for future worktree-based verification in this project.

## 2026-09-28 — Convert-media: staging directory for atomic `processed/` writes; `--ignore-xmp`; rotating file log

- **Context:** Investigated two invisible failures from a real convert run on the user's library: (1) `error/IMG_5234.dng` (iPhone ProRAW) failed because `avifenc` rejects the embedded RAW preview JPEG's duplicate XMP APP1 segments (`XMP extraction failed: invalid multiple standard XMP segments`); (2) 3 of 14 `processed/*.avif` files had no `.thumbnails/*.jpg` — traced to a race where `ConvertMedia._encode_once` wrote `avifenc` output straight into `processed/`, then ExifTool rewrote it in place, so for a window each output was partial/missing/renamed while `SyncGalleryIndex` (running concurrently on every gallery fetch) could index a half-written file, hit a thumbnail-generation `ToolExecutionError` (uncaught by `/thumbs/…`, since it only caught `OSError`), or see the file as removed mid-swap and delete its thumbnail — which then stayed missing forever because the browser's long `Cache-Control` never asked again. A thumbnail-generation crash and the broad job-crash `except Exception` handlers in `bootstrap/services.py` also had no persistent record — only `str(exc)` in an in-memory field, gone on restart.
- **Decision:** (a) Add `--ignore-xmp` to the `avifenc` invocation (safe because ExifTool always re-copies all metadata from the original afterwards). (b) `ConvertMedia._encode_once` now encodes into a same-volume staging path (`{library_root}/.convert-staging/…`, via `domain/gallery_cache_paths.convert_staging_path`), runs validation/size-rollback against the staging file, and only `filesystem.move_file(staging, dest)`s into `processed/` once fully validated — so `processed/` never contains a partial or in-progress output; `run()` wipes stale staging at start. (c) `SubprocessThumbnailGenerator.ensure_thumb` writes to a `dest.with_name(dest.name + ".tmp.jpg")` temp file and `os.replace`s it into place, so a reader never sees a partial JPEG; on failure the temp file is unlinked and the exception re-raised. (d) The `/thumbs/{relative_path}` route now catches `(OSError, RuntimeError)` (not just `OSError`) and returns 503 instead of an uncaught 500, so the browser's cache never latches onto a failure. (e) New `bootstrap/logging_setup.configure_logging()` attaches one idempotent `RotatingFileHandler` (5MB × 3 backups) to the `"spacemaker"` logger, writing to `{spacemaker_data_dir}/logs/spacemaker.log` (same dir as `preferences.json`); called once from `desktop.main()` before anything else. Every module just uses `logging.getLogger(__name__)` and relies on propagation. Added `logger.warning`/`logger.error` at every previously-silent failure point: per-file encode failures/retries in `convert_media.py`, thumbnail generation failures in `subprocess_thumbnails.py` (before re-raising) and at the `/thumbs` HTTP boundary, and `logger.exception` alongside the existing `str(exc)` capture in the `services.py` job-crash handlers.
- **Rationale:** Atomic writes (staging + rename, temp + replace) are the standard fix for "reader sees partial file" races and require no locking between the convert job and the concurrent gallery sync. `--ignore-xmp` loses nothing since metadata is always re-applied from the source. Persistent rotating logs turn silent, one-shot failures (which is what both bugs above were) into something diagnosable after the fact without re-running with `--server-only` and watching stdout.

## 2026-09-28 — webnav: prefer npm `.cmd` shims on Windows

- **Context:** Live smoke on Windows found webnav's JS/HTML/CSS language servers failing with `File not found: None` / WinError 193. Two stacked causes: (1) incomplete `node_modules` (only Biome present — language-server packages never installed), so resolution fell through to bare `npx`; (2) even after `npm ci`, `_resolve_bin` preferred the extensionless POSIX shim under `node_modules/.bin/`, which `CreateProcess` cannot run (WinError 193 "%1 is not a valid Win32 application"). `format_tool_error` also rendered spawn failures without a filename as the misleading `Cannot read None: …`.
- **Decision:** Prefer `{bin}.cmd` before the extensionless shim when `sys.platform == "win32"`; resolve `npx` via `shutil.which` in the fallback; improve spawn-error text when `exc.filename` is None. Documented in `docs/agent-tooling.md`. Unit tests in `webnav_mcp/tests/test_lang_command.py`.
- **Rationale:** Matches how Windows npm actually lays out `.bin/` and how CreateProcess works; keeps the POSIX path unchanged. Incomplete installs remain a local hygiene issue (`npm ci`), not something the resolver can invent binaries for.

## 2026-09-24 — Fixed the SelectorEventLoop fix itself: uvicorn's custom `loop=` string must resolve to the loop class directly, not a factory function; added a real-process smoke test

- **Context:** The previous entry's `event_loop.py` fix (`uvicorn.run(..., loop=uvicorn_loop_for_platform())` pointing a `"module:attr"` string at a `windows_selector_loop_factory()` function that returned `asyncio.SelectorEventLoop`) looked correct and passed all existing tests, but broke the app outright on the user's Windows machine — the server thread died instantly with `TypeError: BaseEventLoop.create_task() missing 1 required positional argument: 'coro'` and cascading "missing 1 required positional argument: 'self'" errors during shutdown. My function matched the shape of those built-ins (returning the *class*, expecting one more call) but was being used as a *custom* string, which skips that extra call — so `asyncio.Runner._loop` ended up holding the un-instantiated `SelectorEventLoop` class itself, and every subsequent method call on it (`create_task`, `shutdown_asyncgens`, `close`) failed as an unbound-method call.

## 2026-09-24 — `graphify-out/graph.json` / `GRAPH_REPORT.md` will always show an unstaged diff right after a commit — expected, not a bug

- **Context:** After committing GraphRAG tooling (see the entry below), `git status` showed `graphify-out/graph.json` (later `GRAPH_REPORT.md`) as modified immediately post-commit, on both occasions. Investigated via file mtime vs. commit timestamp rather than assuming it would go away.
- **Finding:** `.githooks/pre-commit` runs *before* Git creates the new commit object, so `git rev-parse HEAD` inside the hook can only ever see the **parent** commit — the new commit's hash doesn't exist yet (it's derived from the tree, so a tracked file can never embed its own containing commit's hash; that's a hash-cycle, not a missing feature). Graphify's `built_at_commit` field therefore always lands one commit behind in what actually gets committed. Separately, Graphify's clustering step re-touches the file a few seconds *after* the hook's `git add` (confirmed via mtime: file changed ~3s after the commit timestamp), re-stamping it with `HEAD` as of that moment — which by then is the *new* commit, since the ref already advanced. That second, unstaged write is the actual diff `git status` shows.
- **Decision:** Documented instead of "fixed" — there is nothing to fix. Re-running the hook or re-committing does not resolve it; it reproduces the identical one-commit-behind drift on the *next* commit. Don't spend time chasing this again.
- **Rationale:** Any tool that stamps a generated artifact with "the commit that produced me" has this same inherent limitation. Silently accepting a permanently-slightly-dirty `git status` after touching graph files is less confusing than a future session assuming it's a regression and trying to patch it.
